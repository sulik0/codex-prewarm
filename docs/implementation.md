# 实现细节

本页按当前代码说明具体判断和边界，核心模块之间如何配合见[项目架构](../ARCHITECTURE.md)。

## 查询账号和额度

`prewarm.py` 先读取配置中的 Codex 登录文件，比较账号哈希值，并拒绝使用 API Key 的登录方式。随后启动 `codex app-server --stdio`，依次发送 `initialize`、`initialized` 和 `account/read`，确认返回的是 ChatGPT 账号。

查询使用 `account/rateLimits/read`。脚本优先取 `rateLimitsByLimitId.codex`，没有时再取 `rateLimits`，并按 `windowDurationMins` 找到 300 分钟和 10080 分钟的额度。它检查使用百分比是否为 0 到 100 之间的有限数值。

每次 RPC 等待最多 40 秒。查询失败时，`read_quota()` 最多启动三次查询，重试前分别等 10 秒、20 秒。无法取得五小时重置时间、找错额度类别或取得无效数值时会失败，不据此发送请求。周额度无法确认时，也不会进入正常发送。

## 判断计时是否已经开始

`window_state()` 先计算重置时间距离当前时间还有多久：

| 情况 | 返回值 | 后续处理 |
| --- | --- | --- |
| 重置时间已经过去 | `expired` | 后续还需检查周额度，再决定是否发送。 |
| 距离重置不到 17910 秒 | `active` | 正常定时执行直接跳过发送。 |
| 尚不能判断 | `uncertain` | 再等 15 秒查询一次。 |
| 两次重置时间差不超过 2 秒，且第二次仍未到期 | `active` | 认为计时已在进行。 |
| 两次查询间隔至少 10 秒，重置时间向后移至少 6 秒，而且移动量与查询间隔相差不超过 5 秒 | `idle` | 认为接口还在显示随当前时间移动的预计重置时间。 |
| 其他情况 | `uncertain` | 正常发送停止，记录无法确认的原因。 |

使用量为 0% 不参与这个判断，所以它不能单独证明计时尚未开始。

发送后，`stable_new_window()` 要求两次重置时间相差不超过 2 秒、第二次读数仍未到期，并落在“发送前记录的时间加五小时减 90 秒”到“请求完成时间加五小时加 90 秒”的范围内。

此外，发送前必须已判断为 `idle`，或者旧重置时间已经过去，或者新重置时间与旧值相差超过 2 秒。这样才能区分新的计时和原来就存在的计时。每组读数间隔 15 秒，最多检查三组；组间再等 15 秒，不会重新发送模型请求。

## 发送什么请求

`send_request()` 在临时空目录运行 `codex exec`，要求回复 `OK`，并要求不使用工具、不检查文件。请求使用本项目指定的模型、低推理强度、只读沙箱、`--ephemeral` 和 `--ignore-user-config`，不等待交互审批。

脚本最多等 120 秒。CLI 必须正常退出，并且 JSON 输出中存在 `turn.completed`，脚本才认为请求完成。代码不检查回复文本是否逐字等于 `OK`；它只提取输入、输出和缓存输入 tokens 的数量。

原始 CLI 输出和错误输出不写入项目日志。已知模型、认证和超时错误会转换成简短分类。CLI 本身可能在一次调用内部重连；项目不会因为结果不明而再启动一次发送。

## 运行模式和防止重复发送

| 启动方式 | 行为 |
| --- | --- |
| `--scheduled` | 检查当天时间点和补跑宽限，并在发送前记录该时间点已尝试。 |
| `--probe` | 查询当前额度并写入最新状态，不发送模型请求。 |
| `--test-send` | 可在已有有效计时中发送一次测试消息，但仍检查账号和额度。 |
| 不带参数 | 不检查计划时间；如果额度状态允许，可能直接发送，也不记录计划时间点。 |

所有模式先用 `flock` 获取 `run.lock`。已有脚本运行时，新进程只向标准输出打印 `already_running`，不会更新状态文件。

定时模式只接受当天配置时间点之后、补跑宽限以内的执行。每个时间点发送前先把 `last_slot` 和尝试时间写入 `state.json`；再次执行同一时间点时，返回 `duplicate_slot_skipped`。已有计时直接跳过的情况不写发送尝试记录。

正常流程先处理已有计时，再处理周额度。因此即使本轮使用量已达 100%，只要计时尚未到期，定时结果仍可能是 `existing_window`。`--test-send` 允许走过这个跳过条件，但不会在已用完的活动额度中发送。

## 保存结果和退出码

每次正式记录结果时，脚本用临时文件替换 `status.json`，再写入 `prewarm.log` 和标准输出。它不把请求内容或登录令牌写入这些文件。发送尝试另保存在 `state.json`。

整个预热进程使用 480 秒报警限制；它不等同于系统唤醒维护脚本的超时限制。文件保存位置和日志轮转见[部署说明](deployment.md)。

| 退出码 | 含义 |
| --- | --- |
| `0` | 查询、核验或正常跳过已完成；不代表一定发了请求。 |
| `1` | 账号、查询或请求等步骤失败。 |
| `2` | 请求完成，但新的计时未确认。 |

状态名称和常见原因的处理方法见[排错说明](troubleshooting.md)。

## 系统如何维护唤醒计划

系统 plist 安装后立即运行 `wake.py`，之后每天 00:05 再运行。脚本遍历今天及之后八天，为每个发送时间安排提前一分钟的 `pmset schedule wake`。已过去的时间不再安排，已有相同标记的事件不会重复添加。

标记格式为 `local.codex-prewarm.YYYYMMDD-HHMM`。脚本先读取系统安排，只添加缺少的本项目事件；取消模式也只尝试撤销当前时间表和九天范围内存在的对应事件。不会使用 `pmset repeat cancel` 或清空全部计划。

结果写入 `wake-status.json`，包括本次新增或取消的事件，以及执行失败的事件。当前 `pmset` 子进程没有单独设置超时；安装和维护是否成功应看结果文件及任务退出码。

## 检查脚本能确认到什么程度

`healthcheck.py` 读取任务是否加载、任务退出码、剩余标记事件、最新状态和保留日志中的历史结果。只有找到 `new_window_verified`，才填入 `latest_verified_new_window`。因此该字段为空表示保留日志中没找到成功记录，不代表日志保留范围之外从来没有成功过。

对最近六次有时间点的记录，它查找计划唤醒时间前后 20 秒内的 `Wake`，要求任务在计划之后 30 分钟内完成记录，再查找此前休眠、本项目唤醒请求，以及记录之后十分钟内再次休眠的事件。缺少的关联信息会保留为 `null`。

这些时间关联可以帮助确认 Mac 曾醒来并执行任务，不能单独证明是谁导致了唤醒，也不能证明新的额度计时已经开始。检查子命令每次最多等 25 秒；脚本不执行实时额度查询。
